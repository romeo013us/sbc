# Publication receipt ledger candidate

This is offline reconciliation, not a publisher, scheduler or live provider adapter. It requires a dedicated non-reconnecting writer-lock-owning MySQL connection with no existing transaction, trusted account mapping, authenticated tenant, genuine immutable accepted submission from the sole authorized publisher, and independent provider post/media readback. The provider may transform JPEG bytes; matching a provider media reference is not proof of the exact bytes displayed. The submission must bind the actual uploaded approved digest to that media reference. Missing or conflicting provider evidence must be held for review, never fabricated or replayed.

The receipt, source history and existing campaign registry are appended together in one transaction, with same-session lock checks and exact approved inventory/readback join. The readback must have preceded submission by no more than one hour. Historical receipt reconciliation does not grant publishing permission, and does not erase a fact just because a review was later revoked. Duplicate slot or registry collisions require operator reconciliation; the ledger deliberately does not silently treat them as accepted, and must not be used to conceal actual duplicate posts. If a commit is uncertain, destroy the connection and re-evaluate the writer lease, then independently reconcile durable state before any further attempt. Never run this against a shared transaction or pool that changes sessions.

The new disposable MySQL check relies on tables created earlier in the same CI workflow. The test uses simulated accepted submission and provider readback evidence, not provider APIs. Four focused unit tests passed locally; the MySQL acceptance file passed syntax checking only. Real MySQL execution, authenticated provider binding, immutable submission storage, live integration, and operational exception recovery remain required.
