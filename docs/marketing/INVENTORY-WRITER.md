# Append-only marketing inventory writer candidate

createInventoryWriter is an offline trusted-operator adapter for the three proposed inventory tables. No production route, worker, schedule or migration is enabled. Use a dedicated, non-reconnecting, autocommit MySQL connection that itself owns the existing runtime advisory lock, with INSERT and SELECT only. Never acquire the lock by evicting Published, or use a pool that can switch sessions. The caller must enforce owner/tenant authorization, independently verified original logo, allowed campaign slugs, current recovery/role state, and provide genuine stageSocialJpeg metadata from an actual private render. A stage receipt and actorId supplied by an arbitrary client are not trusted. The function does not read staged bytes itself. The approval operation requires an actual authorized human review of exact JPEG bytes. Do not expose the injected verify dependency to clients; it is a test seam.

Each append requires the expected current revision and includes a same-session IS_USED_LOCK=CONNECTION_ID condition and revision CAS directly in the INSERT. Staging inserts an unapproved revision; approval inserts a separate revision with actor, exact digest and time, never overwriting old evidence. Readback normally calls verifySocialDeploy and accepts a receipt for that exact approved digest and format, at most 60 seconds old (initial persistence threshold). Current Creative Studio source review is rechecked before writing. Known used source and digest are excluded in SQL. No automatic retry after a duplicate, failed or ambiguous write; inspect and reconcile durable state before any retry. Never call concurrently on the lease connection. A true database integration and cross-store revocation race review are still required; the MySQL lock does not make the independent SQLite review store transactional.

The publication history writer is deliberately deferred until actual provider account/receipt verification exists. No new post, history entry, queue job or image is generated here. Tests use a fake SQL connection and injected receipt fixture, not real MySQL or HTTP; they check exact revisions, review and digest matching, writer rejection and no replay, not actual SQL lock enforcement. The existing proposed DDL remains inactive. Before integration run disposable MySQL lock-loss and concurrent/stale-write tests, real renderer and review-store tests, and readback verification with real bytes. No live DDL or production changes.

The legacy v6535 test imported a removed patch and assumed mutation workers should start without DDL opt-in. Its replacement executes the actual current startup guard prefix against all 32 flag combinations; it verifies entry to the mutation-worker boundary and separate existing-schema advisory entry, not internals of those workers. No server behavior changed.
