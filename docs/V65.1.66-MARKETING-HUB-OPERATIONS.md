# SBC V65.1.66 Marketing Hub — Operations

## Workflow

1. Draft content manually or use **Draft with Kim**. Kim generation calls the existing authenticated `/api/ai/chat` endpoint and falls back to manual writing if that service is unavailable.
2. Save the draft. The published writer runtime stores it in the tenant-scoped `sbc_marketing_content` table. If the writer/recovery gate is closed or the API is unavailable, the UI labels the item as browser-local; local items do not publish automatically.
3. Submit the draft for owner approval. The approval route requires the authenticated owner role.
4. An approved item can be published immediately or scheduled. Scheduled items are processed by a bounded worker only when MySQL is available, the runtime is a writer, recovery evaluation completed, recovery is not required, and the writer lease is ready.
5. The worker verifies provider identity/access before claiming a scheduled item. Provider publish failures are marked `FAILED` and are not automatically retried, to avoid duplicate public posts after ambiguous network failures.

## Safety gates

- The marketing table is created only on an authenticated owner write when the runtime is not read-only, recovery evaluation has completed, recovery is not required, and the writer lease is ready. Preview/read-only mode does not create or migrate this table.
- All content reads/writes are tenant-scoped. The code does not fall back to tenant 1 for a missing tenant identity.
- Only owner-approved content can be published.
- Instagram publishing requires a public HTTPS image URL.
- External publishing requires live provider verification. A saved token alone does not count as a verified connection.
- Scheduled posts remain queued if credentials/provider verification are unavailable. Once claimed for a publish attempt, failures are recorded and not retried automatically.
- The UI's Analytics tab currently reports content/approval/scheduling/publish counts from SBC records. Reach, impressions, clicks, conversions, CAC and ROAS are not reported until provider insights and conversion attribution are implemented.

## Session-store backpressure

The session patch coalesces concurrent durable reads for the same session token, bounds concurrent durable lookups, throttles reads briefly after a store failure, reduces last-seen writes to at most once per minute per token, and returns a `Retry-After` hint on `SESSION_STORE_UNAVAILABLE`. It fails closed; it does not bypass session validation or recovery protection.

This is a mitigation for queue pressure, not proof that the live GoDaddy session store is healthy. Verify authenticated `/api/me` and `/api/agent-os/status` requests after deployment and inspect durable-store queue depth/latency before declaring production healthy.
