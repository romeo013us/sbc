# V65.1.65 API Circuit Breaker — rollout notes

## What the logs establish

The supplied GoDaddy log shows a successful V65.1.64 process startup, but repeated slow requests, aborted requests, durable-session reads failing with `Queue limit reached`, and restricted session verification failing with `SESSION_STORE_UNAVAILABLE`. Tenant-dependent background jobs are also being rejected without tenant context. These are separate signals; the log does not establish that any one alone caused every browser 503.

## V65.1.65 frontend safeguard

This overlay trips after two consecutive HTTP 503s or network failures from `/api/me` and `/api/agent-os/status`. It adds one non-duplicating `STANDBY_GUARDED` notice and suppresses repeat core endpoint calls for 30 seconds before allowing a read-only recovery probe. A successful response closes the notice. It does not clear state, reload the page, mutate CRM/business data, bypass session validation, or unlock recovery.

## Required backend work (not solved by the browser circuit breaker)

1. Trace the durable session-store queue limit to the exact queue implementation and producer/consumer rates.
2. Bound and single-flight session-store reads; return explicit 503 + Retry-After when saturated.
3. Audit autonomous sweeps: reject/skip tenant-dependent work before enqueue if no validated tenant context; prevent rejected work from filling a retry queue.
4. Add queue depth, queue wait, DB pool in-use/free, route latency and boot_id metrics.
5. Reconcile the duplicate GoDaddy deployment starts and verify a single effective release/asset manifest.
6. Run regression suite and confirm real production API status before Marketing Hub rollout.

## Release gate

Do not declare production fixed until `/api/me` and `/api/agent-os/status` succeed with a valid authenticated session, queue saturation is not recurring, and the release's JS/CSS asset identities match. Existing recovery, tenant, and financial controls remain enabled.
