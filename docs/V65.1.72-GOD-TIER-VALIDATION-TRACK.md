# SBC God-Tier Validation Track — Staging First

## Scope

This track combines visual modernization with three non-destructive validation lanes. It does not claim production readiness until the relevant tests run against the exact deployed release and representative staging infrastructure.

## Visual acceptance

- Executive header is compact, wraps safely on narrow viewports, and does not hide the $10,000 owner firewall badge.
- The 10-brain matrix uses five columns on wide screens, three columns at <=900px, and two columns at <=560px.
- The Spanish sales workspace remains route-gated. Its scorecard remains browser-local and must not be treated as CRM, order, payment, or commission truth.
- A changed bootstrap patch identity forces the cached runtime to rebuild and reapply the layout hotfix.

## A — Webhook/concurrency validation

1. Use a dedicated staging database and test-only webhook credentials.
2. Replay the same provider event concurrently (1, 5, 10, 25, then 50 workers); do not target live payment/webhook endpoints.
3. Verify the provider event ID/idempotency key is persisted before downstream business actions and that duplicates do not create extra orders, payments, or fulfillment jobs.
4. Record throughput, p50/p95/p99 latency, memory high-water mark, pool saturation, timeout count, duplicate rejection count, and queue depth.
5. Inject bounded database timeouts and confirm retries are capped, backoff is applied, and the queue remains durable.
6. Stop if error rate, memory, or pool usage crosses pre-agreed limits. Never run an unbounded production spike.

**Pass condition:** one durable logical outcome per provider event; bounded retry/queue behavior; no tenant crossover; no unhandled rejection; measured results attached to the release.

## B — Kim governed patch simulation

1. Use a disposable staging workspace with no production secrets and no write permission to live source paths.
2. Submit harmless and malformed patch candidates; verify syntax checks reject malformed candidates.
3. Test path traversal, absolute paths, symlink targets, oversized patches, unexpected output format, and suspicious tokens. String-denylist checks alone are not a security boundary.
4. Require immutable baseline hashes, a staged diff, test output, owner approval, and a separate deployment step.
5. Confirm rejection and timeout cases leave active source bytes unchanged.

**Pass condition:** all negative tests reject safely; accepted candidates remain staged until explicit owner approval; no automatic production write occurs.

## C — Database integrity and latency review

1. Capture read-only schema metadata, indexes, table row counts, and query plans from staging before proposing DDL.
2. Verify tenant keys and authorization predicates on every tenant-scoped query.
3. Review event-ledger uniqueness constraints against the actual MySQL version and partitioning rules. MySQL partitioned tables impose unique-key restrictions; do not deploy partitioning until those constraints are proven compatible.
4. Measure representative read/write latency and lock waits with realistic staging data.
5. Backups: configure an encrypted, off-host backup destination, retention policy, and alerting only after verifying hosting permissions. Perform a restore drill into a disposable database and record recovery time and point-in-time recovery limits.
6. Do not apply schema-changing SQL from preview/read-only runtime. Use the established published writer/migration process with an owner-approved change and verified backup.

**Pass condition:** no production DDL during review; tenant isolation checks pass; backup restore is proven; query/latency findings and migration rollback plan are documented.

## Deployment gate

- GitHub CI and the full repository test suite pass.
- The exact candidate commit is deployed to staging and its release identity/hash is verified.
- A smoke test confirms login, dashboard, CRM reads, order reads, payment safeguards, recovery safeguards, and sales-route gating.
- Production rollout requires an owner-approved deployment and post-deploy checks. A green CI run alone is not production verification.

## Explicitly not claimed by this document

No live concurrency test, database sync, backup restore, GoDaddy deployment, or production performance measurement has been executed merely by adding this plan. Those require the relevant staging runtime, credentials, logs, and measured results.
