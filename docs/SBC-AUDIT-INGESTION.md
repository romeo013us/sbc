# Offline prospect audit cache ingestion candidate

The new scripts/ingest-prospect-audit.cjs exports a single-record ingestion function for a trusted offline operator. It deliberately has no executable batch entry point until an authoritative current lead loader and a genuine writer-authorization boundary are wired. The loader must resolve the current tenant and lead from trusted CRM state, including all suppression, synthetic-record and verification flags; the caller must provide the approved insert/select-only cache pool without automatic dispatched-write replay. The function rechecks lead eligibility after capture, validates bounded evidence and inserts an immutable row. Identical duplicate records are read back; conflicting duplicates and ambiguous writes are rejected, never automatically replayed. A caller must reconcile uncertain writes before a subsequent retry. The writer callback is not itself a fencing implementation; the deployment must enforce database identity, privileges and writer isolation. Sales Ready is an internal research status, not independent verification or consent.

Five regression tests use injected capture, parser and database fixtures. They run under the existing creative release test glob. Real MySQL ingestion acceptance, authoritative lead loading, rate-limited offline scheduling, live egress verification and retention policy remain necessary. The existing read-model MySQL test covers the proposed table and reader, not this new writer. No production configuration, migration, lead mutation or outreach.

The shared four-migration history is unchanged. Provider binding and campaign tables require independent reviewed payment-object identity, registry and writer contracts. Do not activate proposed DDL or enable cache reads solely because the isolated tests pass.
